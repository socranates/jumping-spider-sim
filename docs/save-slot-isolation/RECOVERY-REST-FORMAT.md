# Private continued schema-3 rests

The immutable first import packet fixes an original life/generation, global proposal and scene-entry kind. It must stay unchanged for transaction restart. Reusing that whole initial packet as every subsequent save would either reject a later generation/scene or rewrite history. `RecoveryRestFormatPrototype` supplies a distinct **continued-rest** payload inside the same explicitly newer rest envelope schema 3.

An active continued payload contains its current checkpoint and scene kind, plus a fixed provenance reference: owner/slot, M1 proposal id, complete original A1 archive descriptors, selected original identity, original life/generation/binding and the original inert recovery-history checksum. It does not nest prior saves, duplicate A1, carry forward the initial global-progress snapshot or replace original history with current actor state. All new outputs are owned/frozen.

`fromProposal(anchor, codec, context)` validates the initial proposal and prepares its continued representation. `advance(prior, currentCheckpoint, context)` retains the provenance exactly while accepting separately validated current state. `retire(prior, newLifeToken, context)` prepares an explicit tombstone carrying the same archive reference. A retired record has no active checkpoint/scene and cannot be revived through `advance`. An ended checkpoint is rejected as an active continuation: ordinary Checkpoint restore resets `lifeOver`, so accepting it there would resurrect a dead life.

`spec(slot, context)` reads the initial packet, continued format, ordinary old checkpoints and old retirement markers through explicit schema-1/2 migration. Ordinary checkpoints with recovered graph history are refused without the provenance wrapper. Older production rest readers refuse the schema-3 envelope before interpreting the body. Main, Free and Easy stay slot/rules scoped. Subsequent generation/rare state belongs to the current checkpoint/global progress; it does not rewrite the original generation binding or historical entry kind. Current mating/hatching/rest entry is classified independently from that original history.

The current-checkpoint path mirrors SaveRest's small identity/character/node/slot bounds and reuses one authoritative Checkpoint decode for history and scene checks. This avoids an extra full graph decode on each continued checkpoint check. Initial proposal preparation still has existing validation/codec passes and cooperates through SaveWork. No latency, heap or frame-rate improvement is claimed from source structure.

## Authority and integration still required

These are pure format readers/preparers, **not an authenticated save writer or gameplay entry gate**. Matching proposal metadata/checksums does not prove a stored A1/M1 exists, grant a lease/life credential or make P/R keys atomic. Before entry or writing, the controller must verify current immutable archive/proposal data, exact selected R identity, fresh owned P lease/global coverage and the same accepted life/intent. It must then use current/backup size caps, cancellation/request/deadline guards, protected CAS and uncached readback. Retirement is a prepared shape, not proof that the server accepted a New Life or death transition.

Production SaveSession/SaveService, codec wiring, client checkpoint wrapping/unwrapping, explicit recovery UI, scene resumption and life credentials remain unconnected. Keep the runtime's enforced `entry_required` hold until that work is verified. Safe fresh-session replacement, schema-3 entry/write/retirement lifecycle, later-slot import using an existing immutable all-slot archive, and original-archive/proposal lifetime across fresh lives remain integration requirements. No archive deletion/pruning is implemented here. The A1/M1 originals stay outside routine rest backup rotation.

Native/full-game compression, cancellation/interruption/takeover/rejoin, all supported scene boundaries, current full adopted gates and release/main/laptop synchronization remain open. Production source is unchanged at 441eaca; this private format has no native or real-service verification and nothing was published. The broad optimization/reliability goal remains active.
