# Periodic recovery request bounds: private candidate

Current production remains f405359, with its separate fresh-read full gates in progress. This budget candidate is not adopted. The exact baseline counterexample shows the periodic SaveSession worker may start three rest-read requests or one lock update plus three rest reads in a single step. With nine legitimate earlier requests represented in its scheduler history, that raises the minute total to12 or13 against the configured cap10. All calls are accounted; the admission check is performed before a batch. This is a reproducible protocol invariant failure, not evidence of live Roblox throttling or lost data.

The private candidate limits periodic rest recovery to one read per step and spreads lease reacquisition and subsequent reads over separate passes. A rotating cursor prevents a failing first slot from starving the others. Progress/heartbeat priority and existing backoff remain. Initial explicit startup load still reads the available slots normally; the new batching rule applies to periodic recovery. Ordinary departure/flush exceptions remain outside this worker budget.

The first attempt delayed the merged-progress callback until all rest reads completed. Although its63 new checks passed, the existing state suite correctly failed1123/1 because a recovered lease must promptly tell the client about merged progress. That source, test and failure are retained under v1-*; v1 type metadata is historical and its individual type logs were superseded, so do not treat that metadata as a current byte-bound proof. The production source was never changed by this experiment.

The corrected candidate sends merged progress immediately, omits unverified rest slots from that snapshot, retains their earlier observations internally, and delivers each freshly verified replacement through the existing rest callback. It clears the partial-reload flag only when all slots have been read. Tests cover equal-timestamp replacements and verify that retained values are not discarded or mislabeled as fresh. The earlier65-check fixture/output/receipt are retained before extending the same candidate with retained-source cases.

Current focused acceptance:82 assertions across rest-read failure, lease failure, exhausted/renewed allowance, completion, prompt progress, per-step/minute bounds, failed-slot fairness, retained observations and fresh replacement delivery. Seven unchanged save suites against the candidate and full strict/compile checks are collected separately; verify-session-budget.py binds their exact results when terminal. No native, real DataStore, full current-game or release claim. Integration still needs native yielding/cancellation/transport checks and a new full gate cohort after any production adoption.

The broader goal remains open: source-bound full tests for the adopted freshness fix, complete progress-preserving historical migration, natural lifecycle/streaming, device/memory/performance and release checks. This candidate does not implement migration or loosen old-world Continue.
