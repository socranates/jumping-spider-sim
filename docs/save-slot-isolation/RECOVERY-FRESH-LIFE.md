# Private fresh life after recovered retirement

The recovered-life owner can now hand an explicit New Life choice back to the normal save protocol. It does not grant a second recovered-life credential or advance a retired checkpoint into an active one. The original A1 archive and M1 proposal remain immutable throughout.

## Same-visit route

1. Complete `retireRecovered(...)` from `RECOVERY-RETIREMENT.md` and wait for `retired`. The old checkpoint credential has been revoked.
2. Call `prepareFreshLife()` and drive Runtime until `fresh_ready` or refusal. Preparation makes a standard schema-2 retirement marker containing only `save_retired` and the already committed boundary token. The authenticated writer rechecks original proposal/archive index/covered owned progress, performs exact raw compare-and-swap against the schema-3 retirement marker, verifies the exact stored candidate uncached and finally rechecks ownership. The result remains nonplayable. The schema-3 marker becomes its normal backup; original source values remain in A1.
3. Call `replaceFreshLife(newServerSessionId, optionalDepartureDeadline)`. This yields through the existing bounded closed departure, preserving later local progress and releasing the owned P lease. It constructs a replacement only after verified preservation/release, no outstanding backend updates, and no busy old owner. The old session and enforced sidecar remain permanently closed. The new server ID must differ; an exact retry returns the one replacement, while a different replacement ID refuses.
4. Load the returned Runtime and enable ordinary offers. Drive its normal worker until the marker is observed, then call `requestFreshLife()`. This selects the actual displayed normal marker only if its identity matches the verified bridge marker. The normal Session performs its existing fresh read, durable New Life retirement and actual intent grant. No grant is synthesized by the bridge.
5. Handle that real decision through the normal client New Life path. Fresh checkpoints use the normal format and new life token, with no inherited recovery history. Subsequent normal Continue follows the usual protocol rather than replaying the original recovery proposal.

The source backend must implement the normal decoded read/update contract. The engine setup uses the production `DataStoreBackend` with the rest codec; the raw recovery adapter must point to the same physical datastore. A backend that exposes compressed bytes as normal decoded reads cannot supply normal offers. The fresh-life tests therefore use the real production adapters over a fault-injected datastore facade, not the preceding raw-memory shortcut. This does not access an online datastore.

## Restart after retirement

An interrupted visit can leave a valid schema-3 retirement marker before the bridge. Ordinary recovery discovery continues to refuse Continue for that marker. An explicit New Life flow may instead call `discoverNewLife(mode)` with both `currentFormat` and `freshWriterFactory=RecoveryCurrentWriterPrototype` installed.

That reader performs its full uncached original archive/proposal/current-marker proof and publishes a protected, nonplayable retirement observation. `acceptRetiredFresh(mode, serial, displayedOfferId)` binds the actual New Life request and selected observation, installs the enforced hold, and transfers the server-only original proof. It grants no credential. The marker writer binds that exact read-only New Life selection, including its revision/choice/current identity. It then uses the same preparation, bridge and closed replacement route. The current explicit request serial is carried into the normal replacement; it does not reuse an earlier visit's request serial by accident.

If a visit ends after the bridge was committed, the standard retirement marker is already readable by the normal New Life protocol. A changed/corrupt checkpoint, changed original proof, lost lease, failed release or changed selection refuses the handoff. Ambiguous writes require exact uncached verification. A refusal after a write does not imply rollback: the next visit reads the actual stored state.
