# Private archive controller

The controller composes the current SaveSession, raw collector, session/Continue guard and immutable archive publisher. It is outside production. Its terminal success is `ready`, meaning that the original archive was written and freshly read back under the private protocol. It does not import progress, grant a life credential, replace a checkpoint or start a new life.

## Ownership and request scheduling

The caller constructs `Controller.new(session, options)`, then `begin(mode, serial, offerId, observationStamp)`, and calls `step(job)` instead of the ordinary session step while the job is pending. Beginning refuses a busy/flushing session. Each step holds the real session's busy flag, including across backend suspension, so concurrent ordinary steps and reentrant controller steps cannot issue another request. Direct load, departure and intent methods still invalidate the captured guard; the integrating server must serialize its own workers and must resume suspended backend threads even after cancellation.

Before any raw collection, an UpdateAsync checks the actual stored progress envelope and requires an unexpired lock owned by this exact session. It changes only known lock metadata, retaining unknown lock fields and every original envelope field. A returned acknowledgement must show that same session and requested heartbeat. An uncertain acknowledgement does not enable collection. The controller retries without treating uncertainty as absence, and refuses missing, invalid, foreign, expired or unexpectedly acknowledged leases.

Every service request is admitted through the session's existing scheduler and counted in its counters. There is at most one request per controller step and at most the configured session allowance in a rolling minute, including heartbeats. The controller caps itself at 96 requests and 900 seconds; configured values may reduce those caps. Heartbeats take priority over archive requests and have a separate retry timer. Archive retries cannot delay a due heartbeat merely because their own backoff has not expired. The retained earlier controller fails the regression for that priority rule. CPU-only work can progress without network allowance while the guard remains valid.

The controller makes its own explicit lease acknowledgements instead of treating the ordinary scheduler's lastBeat field as proof of a successful heartbeat. The ordinary session also uses that field to schedule retries after failures. The shared field still participates in the conservative local guard; neither it nor a past controller acknowledgement proves that a remote lease cannot change after the last request. No destination authority follows from either.

## Immutable archive restart and lifetime policy

After complete raw collection and verification, the selected primary or backup envelope identity must still match the real Continue selection. A fresh archive-anchor probe distinguishes physical absence from errors. Absence starts publication; an existing value starts the publisher's reconstruction protocol. Missing parts may be reconstructed only from matching original raw values. Failed probes/readbacks back off rather than creating a new archive.

Before reconstructed publication can write another part, a cooperative comparison requires every original value to agree with the new raw observation, except for the known progress-lock session and heartbeat metadata. All unknown lock/envelope fields, backups, opaque strings and unselected save slots must agree. This permits the same interrupted archive to survive session restarts while retaining its first complete raw progress value, including its original lock metadata. A later changed save in any slot refuses; it cannot silently reuse or replace the bounded, one-archive-per-owner namespace. Multiple independent migrations/lifetimes will need an explicit retention policy before production integration.

The raw archive can legitimately retain a heartbeat older than the publication operation. The controller does not edit that archived heartbeat to appear current, and does not use it as the current lease credential. It relies on its separate current lease acknowledgements and the selected-source check for this archive-only operation. The standalone fence's stricter matchesPlan age test remains unchanged; the controller does not use that test to reject a correctly retained historical heartbeat. Source collection is still not an atomic multi-key snapshot. A future destination transaction must independently revalidate the selected source and ownership.

## Verification and limits

`verify-recovery-controller.py` reconstructs both executed bundles from current runtime dependencies, validates source/output hashes and checks the full strict-analysis receipt for all five private modules. The current positive run passes 2,621 assertions; the prior controller fails the archive-backoff/heartbeat-priority counterexample. A normal long pipeline takes 22 requests across 133 simulated seconds and exercises CPU progress while quota is unavailable.

The tests use actual SaveSession, SaveIntent, SaveObservation, SaveScheduler and checkpoint/envelope code over MemoryBackend. They cover complete and interrupted archive restart, changed unselected-source refusal, ambiguous archive and heartbeat acknowledgements, source-read and archive-probe failures, backoff, request/deadline limits, foreign and expired locks, superseding Continue while a heartbeat is suspended, cancellation during a suspended archive write, worker serialization and cleanup. Tests retain ordinary queued progress and never grant a life credential. The fixture is a valid generated checkpoint, not an import of Nathan's actual historical save.

No native Studio or real DataStore service test was run for this controller. Request pacing is not measured device performance. Per-component archive/collector bounds do not establish a whole-server memory bound; simultaneous plans, incoming responses and synchronous publisher validation still cost memory and CPU. Provider-wide request/byte budgets and native serialization limits remain integration work. Existing production source and its full Windows/Linux cohort are unchanged.

Next implementation steps are to connect validated legacy offers/selections, implement the portable progress projection and fresh Preserve ecology, design the selected-slot destination transaction and archive-retention policy, then verify native transport and isolated real service/rejoin behavior before release. Main integration, publication and laptop synchronization are still pending.
