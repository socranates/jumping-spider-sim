# Private recovered-life retirement

The continued schema-3 format already supported a provenance-preserving retirement marker, but no authenticated runtime route could store it. A recovered life can now explicitly retire through its existing single save owner. This is the durable retirement boundary, not the fresh-life creation/grant operation or production menu wiring.

## Runtime contract

`Runtime:retireRecovered(mode, oldIntentSerial, oldCredential, oldLife, restSerial, newLifeSerial)` queues preparation without provider access. It requires the actual recovered writable intent and a later whole New Life serial within existing limits. The server derives the boundary token from session ID, slot and new serial; a caller cannot supply an arbitrary life token. The checkpoint ticket uses the existing monotonic rest serial. Pending checkpoint work, another retirement, wrong credentials and unavailable routes refuse admission. While retirement is queued, later recovered checkpoints refuse.

The existing save loop first makes captured progress durable. Preparation checks the original archive/proposal, current initial or continued checkpoint and provenance, then creates the marker with the same original history reference. The authenticated writer freshly verifies M1, the complete immutable A1 index and owned covered P, performs exact raw R compare-and-swap, reads the exact candidate uncached, and finally rechecks P ownership/coverage. Existing deadline, request cap, lease handoff, cooperative preparation and ambiguous-write handling apply. Another changed R refuses rather than being retired by an old capture.

On verified completion the loop installs its terminal `retired` route, clears the cached active checkpoint, adopts the marker identity and revokes the old intent before notifying the decision callback. It emits no ordinary checkpoint-stored receipt and grants no new-life credential. The marker retains the old active record in its normal backup; a new discovery refuses the retired primary rather than offering that backup or replaying the immutable initial proposal. A1 and M1 are untouched. The terminal route maintains only the progress lease until explicit departure, which preserves pending local progress and releases its own lease through the existing bounded departure owner.

If preparation is cancelled before the write, the prior checkpoint remains unchanged. A write with a lost response is resolved by exact readback/retry. Cancellation or lost ownership after a write cannot promise rollback: the marker may be durable while the local outcome is refused, and a later session must discover the actual stored state. No transaction spans R and P atomically; the existing proof/lease protocol still governs the boundary.

## Evidence and remaining gates

The retirement cohort covers all three slots, dirty captured progress, late old checkpoints, duplicate/invalid admission, terminal idle/departure with later progress edits, a yielding decision callback/departure, a separate returning factory, active-backup refusal, lost responses both before and after a write, changed raw checkpoint refusal and departure during preparation. Final `retirement-attempt-3-*` passes 17,253 retirement assertions plus 128,847 preceding assertions, 146,100 total with zero failures. Entry compilation and full strict analysis of all 33 private candidates pass in `retirement-types-3-*`. `verify-recovery-retirement.py` checks current inputs, assembled bundle, outputs and type hashes; its result is `recovery-retirement-verification.json`. The unchanged budget observer retains its preceding narrow native proof, not retirement/native-service proof. Attempt 1 retained a strict nullable warning and an overly narrow cancellation-test quota assertion; attempt 2 passed before the final memory cleanup and additional callback/continued cases. Earlier receipts remain historical after those code changes.

This remains private and in memory. Explicit fresh-life entry, preserving the original archive across later-slot imports/new lives, safe replacement of the terminal session, production SaveService/client/remote/menu integration, full native recovery/retirement and online datastore/rejoin verification remain open. No published-game or normal player save has been changed. The broader optimization/reliability goal remains active.
