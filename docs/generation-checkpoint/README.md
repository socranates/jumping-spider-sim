# Keep the newborn before its first rest

## Problem and policy

Claude's quick review identified a real gap. The parent could not save during hatching, and Carry only dirtied account progress. Returning before the child's own first rest therefore restored the parent's hatch-morning checkpoint. The retained pre-fix reproduction in `before.txt` returned `mating=hatched`, generation zero and the parent's life seed after Carry.

Each new generation now receives one automatic checkpoint, at Carry's starting position or Follow's actual landing. This uses the existing asynchronous private preparation and owned R-save path. It does not introduce mid-life autosaves or change the ordinary Rest control. A return while it prepares queues behind the child snapshot; Cancel cancels that return while allowing the baseline to finish. Starting a different life revokes both the old worker and queued return.

The optional `checkpoint_origin="generation_start"` metadata is accepted only for a living, awake, unmoulted newborn with no previous growth credit or reproductive stage. It gives Back the appropriate notice. Ordinary and older checkpoints need no new field or schema conversion. The previous parent checkpoint remains an exact backup.

If private preparation fails or its source is revoked, the child remains in play, the earlier stored bytes remain intact, and Back refuses to replay the parent. A successful later child rest clears that guard. Parents no longer hand the child their resting/sleep state, held prey, feeding animation, captured-rival grip or unfinished strike. Releasing unfinished prey conserves remaining nutrition and gives no extra food/meal credit; the existing family meal history remains intact.

Online durability still requires the existing server acknowledgement. Closing before preparation/upload finishes or while the provider is unavailable cannot guarantee a saved child. The UI must not call this Saved prematurely. There is no new storage protocol, lease bypass or permission to overwrite a foreign/protected slot. Corrupt-record fallback remains part of the separate recovery audit; this change does not promise to repair arbitrary corruption in a saved baseline and its backup.
